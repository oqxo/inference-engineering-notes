# LLM Inference & Serving — Reference Notes

## 1. Big Picture

When you send a request to an LLM:

```text
User Prompt
    ↓
Tokenization
    ↓
Tokens
    ↓
Prefill
    ↓
Decode
    ↓
Output Tokens
```

There are two major runtime phases:

```text
PREFILL                         DECODE
Read input                      Generate output
─────────────────               ─────────────────
All prompt tokens               One token at a time
Mostly parallel                 Sequential
Compute-bound                   Memory-bandwidth-bound
Determines TTFT                 Determines ITL
```

The most important concepts are:

* **Tokens**
* **Prefill**
* **Decode**
* **Attention**
* **KV Cache**
* **TTFT**
* **ITL**
* **GPU memory**
* **Concurrent requests**

---

# 2. Tokens

An LLM does not fundamentally operate on words.

It operates on **tokens**.

A token can be:

```text
whole word
word fragment
punctuation
symbol
part of code
```

For example:

```text
disconnecting
```

might become:

```text
disconnect + ing
```

Therefore:

```text
100 words ≠ necessarily 100 tokens
```

The exact number depends on the tokenizer and the input.

### Why tokens matter

Tokens affect:

1. **Cost**
2. **Context-window usage**
3. **Compute**
4. **KV-cache memory**

So when thinking about LLM infrastructure:

> **Always think in tokens, not words.**



---

# 3. Decoder-Only Model

Most modern chat LLMs use a **decoder-only architecture**.

Its fundamental job is:

> Given everything seen so far, predict the next token.

Example:

```text
Input:

"The capital of France is"

Model predicts:

"Paris"
```

Then:

```text
"The capital of France is Paris"
```

The model predicts the next token again.

Therefore generation is:

```text
Token 1
   ↓
Token 2
   ↓
Token 3
   ↓
Token 4
   ↓
...
```

This is called **autoregressive generation**.

"Autoregressive" simply means:

> The model uses its previous output as part of the input for producing the next output.



---

# 4. Embeddings

Before the neural network can process a token, the token is represented numerically.

For example:

```text
"cat"
  ↓
token ID
  ↓
embedding vector
  ↓
[0.12, -0.43, 0.87, ...]
```

An **embedding** is simply a numerical representation of a token that the neural network can operate on.

Think:

```text
Text
 ↓
Token
 ↓
Numbers
 ↓
Neural network
```

---

# 5. Attention

This is an important term.

The model needs to determine:

> **Which previous tokens are relevant to the token I am currently processing?**

That's what **attention** helps it do.

Example:

```text
"The server crashed because it ran out of memory."
```

When processing:

```text
"it"
```

the model needs to understand that:

```text
"it" → "server"
```

rather than:

```text
"it" → "memory"
```

Attention allows tokens to look at relevant previous tokens and determine how much they should matter.

Conceptually:

```text
Current token
     │
     ├──── looks at previous token
     ├──── looks at previous token
     ├──── looks at previous token
     └──── looks at previous token

        ↓

Relevant information
```

This is how the model maintains relationships and context between tokens.

The course describes attention as allowing each position to look back at earlier tokens and pull in what matters. 

---

# 6. Prefill

Suppose your prompt contains:

```text
500 tokens
```

The model receives all 500 tokens at once.

This is **prefill**.

```text
500 input tokens
       ↓
    PREFILL
       ↓
Model processes prompt
```

Because the entire prompt already exists, the model can process those tokens **in parallel**.

### Prefill characteristics

* Input-side computation
* Parallelizable
* Primarily **compute-bound**
* Larger prompt → more prefill work



---

# 7. TTFT — Time To First Token

TTFT measures:

```text
Request sent
     ↓
[model processes prompt]
     ↓
First output token
```

So:

> **TTFT = time from sending the request until the first generated token arrives.**

Long prompt:

```text
10,000 tokens
      ↓
Large prefill
      ↓
Higher TTFT
```

Short prompt:

```text
100 tokens
     ↓
Smaller prefill
     ↓
Lower TTFT
```

Therefore:

> **Prompt length primarily affects TTFT.**

---

# 8. Decode

After prefill, the model starts generating.

Suppose it needs to produce:

```text
"Paris is the capital of France."
```

The model generates approximately:

```text
Paris
  ↓
is
  ↓
the
  ↓
capital
  ↓
of
  ↓
France
  ↓
.
```

One token at a time.

This is **decode**.

Unlike prefill, the next token depends on the previous generated tokens.

Therefore decode is inherently sequential.



---

# 9. ITL — Inter-Token Latency

ITL measures the time between generated tokens.

Conceptually:

```text
Token 1 ──100ms── Token 2 ──100ms── Token 3
             ↑
            ITL
```

So:

> **ITL = how quickly the model generates subsequent tokens.**

Long answer:

```text
1000 output tokens
        ↓
1000 decode steps
```

Therefore:

> **Output length primarily affects total generation time.**

The course describes decode as primarily **memory-bandwidth-bound**, because each step needs to move model weights and runtime state through memory. 

---

# 10. TTFT vs ITL

This distinction is extremely important for production.

| Problem                                   | Main thing to investigate |
| ----------------------------------------- | ------------------------- |
| First token takes too long                | **Prefill / TTFT**        |
| Tokens arrive slowly                      | **Decode / ITL**          |
| Very long prompt                          | Prefill                   |
| Very long answer                          | Decode                    |
| "Why did response take so long to start?" | TTFT                      |
| "Why is response streaming so slowly?"    | ITL                       |

Mental model:

```text
                 REQUEST
                    │
             ┌──────┴──────┐
             ↓             ↓
          PREFILL        DECODE
        prompt tokens   output tokens
             │             │
             ↓             ↓
           TTFT           ITL
```



---

# 11. KV Cache

This is the most important memory concept for LLM serving.

During attention, the model calculates information associated with each token called:

```text
K = Key
V = Value
```

These are stored in memory.

That storage is called the:

> **KV Cache — Key-Value Cache**



---

## Why do we need it?

Imagine generating:

```text
Token 1
Token 2
Token 3
Token 4
...
Token 1000
```

When generating token 1000, the model needs information about previous tokens.

Without caching, it would repeatedly recompute information for earlier tokens.

That would be extremely wasteful.

Instead:

```text
Token 1 → calculate K,V → store
Token 2 → calculate K,V → store
Token 3 → calculate K,V → store
...
```

Then later:

```text
Token 1000
    ↓
Read existing K,V
    ↓
Don't recompute them
```

So the KV cache is essentially:

> **Persistent attention state for the tokens already processed by that request.**

The course compares it to rough work in an exam: calculate something once, keep it, and reuse it later. 

---

# 12. What is actually stored?

For each token, attention produces:

```text
Key
Value
```

Conceptually:

```text
Token 1 → K1 V1
Token 2 → K2 V2
Token 3 → K3 V3
Token 4 → K4 V4

             ↓

        KV CACHE
```

When another token arrives:

```text
Token 5
   ↓
Attention
   ↓
Uses:

K1 V1
K2 V2
K3 V3
K4 V4
```

Then it creates:

```text
K5 V5
```

and adds them to the cache.

So the cache grows as the request progresses.

---

# 13. KV Cache Memory

The course gives the fundamental relationship:

```text
KV memory / request
≈
KV cost per token × number of tokens
```

And with concurrent requests:

```text
Total KV memory
≈
KV cost/token
×
tokens/request
×
concurrent requests
```



This is extremely important for GPU capacity.

---

# 14. Why Context Length Matters

Suppose:

```text
Request A = 1,000 tokens
Request B = 10,000 tokens
```

Request B needs roughly **10× the KV-cache space**, assuming the same model and cache format.

Therefore:

```text
Longer context
      ↓
More KV memory/request
      ↓
Fewer concurrent requests
```

This is why a model supporting a huge context window doesn't mean you can run huge numbers of concurrent users.

---

# 15. GPU Memory Is Not Just Model Weights

Suppose a GPU has:

```text
80 GB VRAM
```

You cannot simply say:

```text
80 GB / model size = users
```

Because GPU memory is consumed by multiple things:

```text
GPU VRAM
│
├── Model weights
├── KV cache
├── Activations / temporary buffers
├── Runtime/framework overhead
└── Other serving overhead
```

For concurrency, **KV cache becomes particularly important**.

---

# 16. Worked Example — 7B Model on 24 GB GPU

This is a **worked infrastructure example**, not a number supplied by the course.

Assume:

```text
Model:        7B parameters
Quantization: 4-bit
GPU:          24 GB VRAM
```

Very roughly:

```text
7B × 4 bits
≈ 3.5 GB raw weight storage
```

But the actual loaded model will consume more than the raw arithmetic because of metadata, runtime buffers, etc.

Let's use a simplified planning assumption:

```text
Model + runtime = 6 GB
```

Then:

```text
24 GB GPU
- 6 GB model/runtime
--------------------
18 GB available for KV + other serving memory
```

Now suppose, **for this hypothetical model configuration**, the KV cache consumes:

```text
~0.5 MB/token/request
```

And a request uses:

```text
4,000 tokens
```

Then:

```text
KV/request
=
0.5 MB × 4,000
=
2,000 MB
≈ 2 GB
```

Therefore:

```text
18 GB / 2 GB
≈ 9 concurrent requests
```

So the rough capacity is:

```text
~9 concurrent requests
```

**But don't treat 9 as a universal 7B-model number.**

The actual KV cost depends on the model architecture, number of layers, attention heads/KV heads, head dimension, cache datatype, and serving implementation.

---

# 17. The Important Capacity Formula

For a real deployment, think:

```text
Available GPU memory
────────────────────────────
KV memory per request

≈ maximum concurrent requests
```

Where:

```text
KV memory/request
≈
KV bytes/token
×
tokens/request
```

Therefore:

```text
Concurrency
≈
Available KV memory
──────────────────────────────
KV bytes/token × tokens/request
```

This is the key infrastructure mental model.

---

# 18. One User ≠ One Human

This distinction matters in production.

Suppose:

```text
1 human user
```

sends one request.

During that request:

```text
1 active request
```

If 100 users exist but only 5 are generating responses simultaneously:

```text
Concurrent inference requests = 5
```

Capacity is therefore about **active concurrent requests**, not total registered users.

Example:

```text
10,000 application users
        ↓
only 50 active LLM requests
        ↓
GPU needs capacity for ~50 concurrent requests
```

---

# 19. Context + Concurrency Trade-off

This is one of the most important production concepts.

Suppose your GPU can support:

```text
10 requests × 4K tokens
```

You cannot automatically assume:

```text
40 requests × 1K tokens
```

or:

```text
5 requests × 8K tokens
```

because actual serving has scheduling, batching, memory fragmentation, model architecture, and other constraints.

But the basic relationship is:

```text
More tokens/request
        ↓
More KV/request
        ↓
Less concurrency
```

and:

```text
More concurrent requests
        ↓
More total KV memory
```

## Final cheat sheet

```text
TOKEN
= unit the model processes

PREFILL
= process the entire input prompt

TTFT
= time until first output token

DECODE
= generate output one token at a time

ITL
= time between generated tokens

ATTENTION
= mechanism that lets tokens use relevant information
  from other tokens in the context

KEY (K)
= attention information used to determine relevance

VALUE (V)
= information retrieved/used once attention selects it

KV CACHE
= stored K/V attention state reused during generation

KV MEMORY
≈ KV bytes/token × tokens/request

TOTAL KV MEMORY
≈ KV bytes/token × tokens/request × concurrent requests

CAPACITY
≈ available GPU memory / KV memory per request
```

The **single mental model I would retain** is:

> **Prefill determines how quickly generation starts. Decode determines how quickly generation continues. KV cache determines how much memory each active request consumes. Therefore prompt/output length directly affects GPU capacity and latency.**
